## Official provider routing and readiness correction (2026-10-23)

New signup completion requires `WHATSAPP_WEBHOOK_CALLBACK_URL`, the trusted server-configured HTTPS endpoint for this deployment (at most 200 characters, without credentials, query or fragment), and `WHATSAPP_WEBHOOK_VERIFY_TOKEN`. Missing or malformed configuration keeps signup unavailable and independently blocks actual group/invitation transport through the shared provider and worker dispatch policy, including jobs queued before a configuration change; loading a disabled integration still works, and an existing connection's read-only health check can still report its status. Callback targets and verification tokens are never accepted from browser signup input.

Before subscription or phone registration, the provider reads the phone's `webhook_configuration` and the WABA's `subscribed_apps`. A different phone-level override or a different callback for this Meta app blocks completion for operator review. An exact existing route is retained without another POST. Otherwise subscription sends the explicit `{override_callback_uri, verify_token}` pair, then re-reads both the phone routing and the exact subscribed app's callback before allowing registration. An empty subscription body is never used: Meta documents that it removes a WABA alternate callback. Ambiguous, paginated, malformed or mismatching readback fails closed; uncertain POSTs are not blindly retried.

The [official override reference](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/override/) supports WABA overrides for group lifecycle, history and SMB synchronization events. Phone overrides take precedence and are checked without modifying them. Account-level events such as `account_update`/partner revocation and template updates always go to the app's default callback. This local change is **not a central offboarding router**. Dedicated deployments with disjoint WABAs can use their own alternate endpoints for supported events, while the app-default account events still need a reviewed common routing path. One WABA must not be independently assigned to several deployments; these read/check/readback calls do not provide an atomic provider-side compare-and-swap against concurrent external configuration changes.

Group eligibility uses the documented `GET /<PHONE_ID>?fields=official_business_account` response and nested `official_business_account.oba_status`. It no longer calls an invented `/official_business_account` edge or accepts a flat status. Only nested `APPROVED`, a connected Cloud API phone, and the existing matching approved invitation template can satisfy the current readiness checks. Ordinary business verification and QR/coexistence connection remain distinct from group eligibility. See [Official Business Accounts](https://developers.facebook.com/documentation/business-messaging/whatsapp/official-business-accounts/).

The exact October 23 official page content and hashes are retained in `outputs/office-whatsapp-20261023/research/official-meta-docs-20261023.json` and `official-meta-webhook-routing-20261023.json`. Fake HTTP contract evidence is recorded separately from actual Meta approval or live delivery.

## User flow

- Platform settings → **חיבורים למשרד**. The office is determined from the authenticated session/deployment. Owners manage their own connection, synchronization time and group defaults. The company/project/customer hierarchy is an internal provider concern.
- Court: save the demo connection and its daily synchronization time. Court numbers are entered on the case create/edit form. The synthetic feed matches those references; repeated syncs do not duplicate events. The case view shows imported demo updates to authorized staff. Test seeding and manual synchronization endpoints remain available for controlled QA, not on the connection settings screen.
- WhatsApp: the owner opens the official Meta Embedded Signup window, chooses the business and number, and grants access. The server exchanges the one-use code, validates app permissions and asset ownership, verifies/configures the trusted callback route, registers the number if necessary, and encrypts the grant per office. No customer copy/paste of access tokens is needed.
- The office owner saves the default invitee numbers, optionally checks **הזמן אוטומטית גם את מנהל התיק**, and enables/disables automatic groups. The manager is resolved from `cases.casemanagerid` and their own office's `users.phonenumber` when the case is created. Numbers are normalized and deduplicated. With the manager enabled, up to six fixed invitees can be saved; otherwise up to seven. Manager-only invitations are supported.
- New cases enqueue one group request transactionally. A worker creates the group; the signed Meta creation webhook attaches its invitation link to the exact case. Each recipient receives the configured group invitation template. The person chooses whether to join; adding people without their acceptance is unsupported.
- In demo mode there are no external calls and no invented WhatsApp links. Court demonstration cases use a synthetic manager number when the checkbox is selected. Demonstration cases are never dispatched in live mode.
- Disabling cancels pending invitations permanently, including when a creation webhook arrives later. Existing external groups remain. Changing defaults or the assigned manager does not change an already queued invitation snapshot.
- A missing/invalid manager phone leaves an explicit `needs_attention` record without preventing case creation. This version does not automatically resubmit that case after a profile correction. An operator must review it; manual database retries must never be used for uncertain remote outcomes.

## Reliability and limits

- Office filters are explicit in service queries and reinforced by database RLS in shared mode. Webhooks route using both the signed WABA ID and phone ID; the job's immutable phone/WABA, unique subject and request ID are checked again.
- Group jobs and case creation commit together. Claiming is persisted before an external mutation. API timeouts and stale creation claims become `uncertain`; there is no blind retry that could create duplicate groups or invitations. Stale claimed invitations likewise become uncertain.
- Template values and recipients are captured for the case. An existing manually linked group is preserved. Court imports do not create calendar events or contact clients. No live Net HaMishpat connector or saved smart-card/session credentials are implemented.
- “Invitations sent” means Meta accepted the send request, not delivered/read/joined. Delivery/participant tracking, retry/reconciliation UI and sending case updates into groups are outside this change.
- The worker handles one group and one invitation per office per tick (15 seconds). Production performance, actual Meta availability, billing setup, account eligibility, template compatibility, and the deployed database schema still require authorized QA with real integration credentials.
