# Durable bulk actions — backend checkpoint, not production ready

Bulk confirmation uses the immutable review ID/hash and payload-bound idempotency. Different keys for the same approval reuse one operation. Different approvals for overlapping package/person targets serialize with incumbent targeted actions, then recompute current permission, profile/task/revision, delivery history and eligibility. Only a subset of the approved targets can be queued. New eligible targets never join. Message/member rows, jobs, operation and replay aliases commit together in bounded bulk SQL writes.

One message represents compatible context/person/endpoint/channel/purpose/policy targets. Per-package member records let targeted actions see pending/cooldown/uncertain bulk delivery, including non-anchor members. The worker locks in incumbent order, rechecks current sender/assignment/contact/link/tasks/artifacts and compares each binding against the immutable original review. Invalid/completed members are explicitly cancelled/skipped. An anchor that changed does not discard other valid selected packages. The freshly issued sign grant has the exact current PDF/task allowlist; read-only copies have only selected readable final documents. No future-stage role/PDF joins.

POST /bulk-actions returns queued, never sent, before provider acknowledgement. GET /bulk-actions/:id is actor/context-private and rechecks package visibility. Revoked assignments expose only the already-known package ID and ACCESS_CHANGED; hidden message/person details and counts are removed. Provider timeouts stay uncertain, with no automatic retry. A reproduced pre-network worker-crash bug was fixed: a quarantined job now reconciles both pending and dispatching deliveries to uncertain rather than leaving an infinite queue indicator. Provider exactly-once is not claimed.
