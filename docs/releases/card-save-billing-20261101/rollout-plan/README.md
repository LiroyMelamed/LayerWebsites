# תוכנית פריסה מדורגת — תכנון בלבד, ללא הרשאה לביצוע

המצב הנוכחי: **אין push, פריסה, שינוי תצורה/נתונים, הפעלת סליקה או משלוח**.
בוצעו רק בדיקות live בטוחות לקריאה בלבד ובדיקות מיזוג לאובייקטי Git מקומיים.
התוכנית מפרידה בין פרסום מקור, פריסת קוד והפעלת חיוב רגיל. אף אחד מהם אינו
אישור לגבייה רטרואקטיבית. כל תוכנית ההתאוששות הפרטנית הקודמת מבוטלת: תקופה
שהבעלים העניק במתנה נשארת במתנה, ללא תיקון שדות או ניסיון גבייה מחדש.
הוראת השימור הפרטנית והראיות נשמרות מחוץ ל־Git.

**לא מוכנים כרגע לפריסה פיננסית.** נדרשים מועמדים סופיים על main החדש,
qualification שלהם, גיבוי/rollback מאומתים, בדיקת סכמות ותצורות ושער מוכח לכל
נתיבי החיוב אם מבקשים פריסת קוד ללא סליקה. אין לפרש את הירוק בבדיקות המקומיות
כאישור לשנות שרת או לגבות כסף.

## 3. תנאי מקדים: מה פירוש פריסת קוד ללא חיובים

**כיבוי scheduler לבדו אינו מספיק.** אימות כרטיס מפעיל ישירות
`collectAfterCardSetup`; גם retry, checkout, annual/upgrade, callbacks ו־return
יכולים לפנות לספק או לסלק תשלום. `BACKGROUND_JOBS_ENABLED=false` אינו שער
לכל הנתיבים. `OFF_KEYS` בכלי Word הקיימים אינו מכסה את חיוב Takbull.

לכן פריסה במצב ללא חיובים חסומה עד שיש מנגנון עצירה שנבדק ומכסה את כל
המפיקים ואת גבול הקריאה לספק, ללא פגיעה בלקוחות/יישומים אחרים. יש להוכיח
עצירת בקשות חדשות, ניקוז פעולות שכבר החלו, שמירת reservations ו־callbacks
ללא איבוד, ואפס קריאות ספק במצב זה. תוצאת pending אינה נמחקת או מסומנת failed
כדי לפתוח ניסיון חדש. השער הזה **טרם מומש/הוכשר במסגרת התוכנית**; אין להציג
דגל קיים כאילו הוא מקיים אותו. אין לשנות תצורה או לעצור תהליך לפני אישור.

גם הפעלה מחדש אינה מטא־דאטה בלבד: startup עשוי לקרוא
`ensureOfficeIsolation` ולבצע בדיקות/פעולות סכמות. לפני אישור יש למפות בדיוק
את פעולות ההתחלה במצב היעד ואת SQL/GRANTs הדרושים. רשימת SQL ברירת המחדל
של החוזה נשארת ריקה; אין הרשאה להריץ את כל migrations/backfill ההיסטוריים.
עצם שינוי הקוד אינו אישור לשינוי שורת חיוב או תקופה שניתנה במתנה.

## 4. קדם־פריסה, גיבוי ו־rollback

לפני ביצוע עתידי, תחת maintenance shared ונעילת יעד מתאימה, יש להקפיא חוזה
לכל משרד: SHA מלא, tree/source hashes, manifest חתימות קיים, תהליך PM2 מזוהה,
cwd/script/port, גרסת Node ותלויות נעולות, frontend archive ו־SHA256,
API/מיתוג/CSP נכונים, preimage תצורה פרטי, מצב schema/app-role ונקודת rollback.
אין `git pull` או build על מקור משתנה, ואין `pm2 restart all`.

יש לבדוק read-only את מצב הסכמה בפועל לפני שמחליטים על SQL, כולל
`users.client_profile`, ההגבלות הרלוונטיות ו־`signing_word_authoring_renders`
עם trigger והרשאות מתאימות. אין להניח שמיגרציית Word עדיין חסרה: המקור כבר
נפרס בעבודה המקבילה. שינוי לא צפוי עוצר; אין יצירת גישה/role או תיקון DB אגב כך.

נדרש גיבוי DB עדכני לכל יעד, עם גודל, hash, תוכן archive שניתן לרשום,
readback מהיעד המרוחק וראיית שחזור בסביבת בדיקה מורשית. בדיקת רשימת קבצים
אינה בדיקת שחזור. **גיבוי R2 שוטף הוא DB בלבד**; מקור נשמר ב־Git מאומת,
ותוצרי rollback ותצורות נשמרים באופן פרטי ומבוקר, ללא סודות ב־Git או בדוח.
יש לשמר לפחות שלוש גרסאות rollback מלאות לכל רכיב ולכבד pins קיימים.
לא נוצר או נבדק כאן גיבוי חדש, restore או rollback.

rollback רגיל מחזיר קוד/ארטיפקט/תצורה מדויקים בבדיקת מצב טרייה, ומשאיר
סכמות additive ואת **כל מצב התשלומים והנתונים העדכניים**. אין לשחזר DB ישן
כדרך לבטל פריסה: הדבר עלול למחוק settlement או את חודש המתנה ולאפשר חיוב כפול.
אם תוצאת ספק לא ודאית, משאירים חיובים מושהים עד reconciliation מאושר;
rollback קוד אינו מבטל עסקה, ואינו הרשאה להחזר/חיוב/מסמך אוטומטיים.

## 5. סדר הביצוע העתידי — QA ואז לקוח אחד בכל פעם

הסדר המוצע הוא **Melamedia QA → AshrafEssa → MorLevi → MelamedLaw**.
QA ראשון הוא כלל מחייב; סדר שלושת הלקוחות הוא בחירת סיכון, לא חובה ברנבוק.
אשרף קרוב למקור המשותף; מור נבדק לאחריו; MelamedLaw אחרון בגלל התרגומים
והצורך לאמת בקפדנות שימור נתונים/תקופות שהובטחו. אין פריסה קבוצתית.

| שלב | פעולה לאחר אישור בלבד | תנאי מעבר |
| --- | --- | --- |
| מקור | לבנות קומיט main אמיתי מהבסיס החדש והתיקון; לסקור את כל ה־diff והתרגומים | source guard, תלויות ובדיקות על אותו קומיט; אין drift |
| QA מקומי | להריץ את רצף החודש החייב והחידוש הבא, כשלים/מרוצים/הטבה; כל בדיקות הממשק ובנייה | בדיקות תקינות; לא להמיר דילוגי סביבה ל־PASS |
| QA שרת | רק עם שער מתאים, גיבוי וחוזה נפרד; לבנות מיתוג ו־API אמיתיים ממקור קפוא | בדיקות read-only אחרי ההעלאה; qualification פונקציונלי מבודד ללא ספק אמיתי עד לאישור נפרד |
| לקוח יחיד | מיזוג main המאושר לתוך ענף הלקוח, סקירה/בדיקות/build מחדש, אישור החוזה שלו | התאמות נשמרו, hashes נקשרים למקור ולתהליך/ארטיפקט, אין אי־ודאות כספית |
| אימות ועצירה | health, תצורה מסוננת, מקור וארטיפקטים; להשאיר שער פיננסי סגור | אין התקדמות ללקוח הבא במקרה חריגה |
| הפעלת חיוב עתידי | פעולה נפרדת ורק לאחר אישור פיננסי מפורש ותנאי הספק | רק מחזורים תקפים שלא ניתנו במתנה; ללא גבייה רטרואקטיבית או תיקון חשבונות |

תוצרי compile קיימים מכילים API מקומי מדומה; **אסור להעלות אותם**. build
הפריסה יהיה חדש ממקור קפוא ועם תצורת הלקוח המאומתת. לפרסם assets לפני HTML,
ולהחליף HTML/manifest רק בסיום תוך שמירת קובצי חזרה. native/store אינם חלק מהפריסה.

אין להריץ את wrappers הישנים כמות שהם: ב־QA wrapper חסר SHA מחייב ונשאר טקסט
Idm; ה־backend wrapper הגנרי כולל יעדים/הרצת SQL שאינם חוזה billing מצומצם.
יש לתקן/להכשיר את כלי ההפעלה או להשתמש בחוזה guarded נבדק עם SHA לכל יעד,
maintenance shared לכל הפעולה ו־tenant mutex exclusive לפריסה/rollback.

## 6. בדיקות live שאינן יוצרות חיוב או שינוי נתונים

מותר: מקור/branch/clean/hash, מידע PM2 מסונן, דגלים לא סודיים, hashes של
manifest/JS/CSS ב־HTTP, ו־GET אנונימי ל־`/health` בלבד. SELECT ממוקד מותר רק
בהרשאה קיימת, ב־`BEGIN READ ONLY`, בלי app bootstrap ובלי ערכי סוד בדוח.

אסור להציג כ־read-only: פתיחת SPA/מסך חיוב, `/plan`, `/plans`, `/lock-status`
או GET מאומת רגיל שעובר `requireBillingAccess`. אלו עלולים ליצור שורת חיוב
או לעדכן grace/status דרך `getBillingSnapshot`. אין payment return/cancel,
checkout, שמירת כרטיס, retry, cron, OTP, ספק או `GetDocumentSettings` — גם GET
אצל הספק עלול לאתחל הגדרות. אין בדיקות כאלה על חשבון שקיבל תקופה במתנה.

תנאי עצירה: ref/source/config drift, נעילה חסרה/תפוסה, protected hash שונה,
target/DB/PM2 שגויים, גיבוי לא מאומת, schema/ACL בלתי צפויים, gate לא מוכח,
pending/unknown payment שלא פויס או קריאת ספק שלא אושרה. אין עקיפה או מחיקת intent.

## 7. הרשאות עתידיות — שלושה אישורים נפרדים, לא בקשה לבצע עכשיו

אין לבקש אישור פריסה עד שהקומיטים/ארטיפקטים והחוזים סופיים ומוכשרים.
הנוסחים הבאים הם דרישות לתוכן אישור עתידי; מזהים חסרים אינם הרשאה כללית.

1. **Git בלבד:** אישור מפורש לפרסם את קומיטי ה־review המדויקים ליעדים המוגדרים,
   לאחר בדיקת טריגרי CI/פריסה אוטומטיים. ללא פריסה, שינוי תצורה או פעולה פיננסית.
   לא נמצאה workflow של GitHub בעץ שנבדק; אוטומציה חיצונית לא הוכחה כנעדרת.
2. **קוד/תשתית בלבד:** אישור ל־SHAs/ארכיונים/סדר יעדים שבחוזה, לגיבוי,
   לשינויי תצורה ו־SQL/GRANTs המפורטים בלבד ול־restart של התהליכים המזוהים;
   רק לאחר qualification של שער החוסם סליקה. אין אישור לחיוב/מסמך/מייל,
   לשינוי שורות חיוב או לתיקון נתוני הלקוח שקיבל את החודש במתנה.
3. **הפעלת חיוב רגיל לעתיד:** אישור נפרד ליעדים, תחילת הפעלה, מחזורי החיוב
   והמחירים המוסכמים שנבדקו בנספח פרטי, ולמסמך/נמען/משלוח שאומתו. האישור
   חייב להחריג גבייה רטרואקטיבית, replay של setup ישן וביטול כל תקופה שניתנה
   במתנה. אין להסיק אישור זה מאישור פריסה. אין בקשת אישור התאוששות פרטנית:
   הצעת ההתאוששות הקודמת בוטלה ולא נשארה ממתינה לאישור.

## 8. חסמים והחלטות שנותרו

- הקומיטים הסופיים על `9f01a42d` ועל כל ענף לקוח עוד לא נוצרו/נבדקו; עצי
  התכנון אינם release. יש להכשיר גם את פתרון התרגומים של MelamedLaw.
- לא קיים כרגע gate מאומת לכל נתיבי הסליקה במצב code-only; כלי הפריסה ופעולות
  startup/SQL צריכים חוזה מצומצם שנבדק. אין ברירת מחדל לאישור כספי.
- סביבת הרשמה מלאה ו־profile PostgreSQL חסרות; אין ליצור סביבה/גישה חדשה
  במסגרת הרשאה זו. נדרש מקור מאושר לסגירת הגייטים או החלטת דחיית הפעלה מתועדת.
- sandbox דורש זיהוי עצמאי ועדכני שאינו מסלק כסף אמיתי. סוג המסמך, ברירות
  המחדל, נמען החיוב בכל משרד ומשלוח הקבלה טרם אומתו. native
  `CreateDocument:true` קשור לגבייה; אין להניח שהפעלת חיוב אינה מפיקה מסמך,
  או לכבות מסמכים כמעקף. אין להפיק/לשלוח מסמך בדיקה ללא אישור נפרד מתאים.
- גיבוי/readback/restore, שלוש נקודות חזרה, schema/app-role ותצורות היעד עוד
  דורשים אימות שחרור. ה־live audit כאן לא הוכיח אותם או בריאות timer/ספק.
- חלון פריסה, אישורי המקור/התשתית/החיוב, פרטי המסמך והתזמון לכל משרד צריכים
  להיקבע על החוזים הסופיים. לגבי תקופת המתנה שבוטלה גבייתה אין החלטה פתוחה:
  משמרים אותה ולא נוגעים בנתונים.
